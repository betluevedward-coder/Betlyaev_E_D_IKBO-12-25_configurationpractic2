# NuGet Dependency Graph Visualizer (Вариант №2)

Инструмент командной строки (CLI) для визуализации графа зависимостей пакетов менеджера пакетов **.NET (NuGet)**. 
Проект разработан в рамках дисциплины «Конфигурационное управление». Строго следует правилам: сторонние менеджеры пакетов и библиотеки для получения зависимостей не используются, все операции парсинга XML и обхода графа реализованы вручную.

## 1. Общее описание

Программа позволяет получать информацию о прямых и транзитивных зависимостях заданного пакета из официального репозитория NuGet, строить граф зависимостей (с обработкой циклических связей), определять порядок загрузки (топологическая сортировка) и визуализировать его в формате диаграмм D2, изображений SVG и текстового ASCII-дерева. 
Приложение поддерживает как работу с реальным URL-адресом репозитория, так и режим тестирования с использованием локального JSON-файла.

## 2. Описание всех функций и настроек (Параметры CLI)

Источником настраиваемых параметров являются опции командной строки:

| Параметр | Тип | Описание | Обязательный |
| :--- | :--- | :--- | :---: |
| `--package` | str | Имя анализируемого пакета (например, `Newtonsoft.Json`) | Да |
| `--repo` | str | URL-адрес репозитория NuGet или путь к файлу тестового репозитория `.json` | Да |
| `--test-mode` | flag | Включает режим тестирования (чтение локального JSON-файла вместо HTTP-запросов) | Нет |
| `--version` | str | Версия пакета (по умолчанию `latest`) | Нет |
| `--output` | str | Имя сгенерированного файла с изображением графа (должно оканчиваться на `.svg`) | Да |
| `--ascii` | flag | Включает вывод зависимостей в консоль в виде ASCII-дерева | Нет |

## 3. Команды для сборки проекта и запуска тестов

Перед началом работы убедимся, что у нас установлен Python 3.9 или выше, а также виртуальное окружение (`venv`).

### Установка зависимостей
Можно установить все необходимые библиотеки для тестирования и линтинга напрямую через `pip` (рекомендуется для Windows) или через `Makefile` (для Linux/macOS):

```bash
# Универсальный способ
pip install -r requirements.txt

# Или через Makefile
make install
```

### Запуск тестов и проверка стиля кода
После установки зависимостей запустите юнит-тесты и линтер:

```bash
# Запуск юнит-тестов (pytest)
pytest tests/
# или
make test

# Проверка кода на соответствие стандартам PEP8
flake8 src/ tests/
```

## 4. Примеры использования

### Пример 1. Анализ реального пакета из репозитория NuGet
```bash
python -m src.nuget_viz.main \
  --package Newtonsoft.Json \
  --repo https://api.nuget.org/v3-flatcontainer \
  --version 13.0.1 \
  --output graph.svg
```

### Пример 2. Работа в режиме тестирования (с локальным JSON-файлом)
```bash
python -m src.nuget_viz.main \
  --package A \
  --repo test_repo.json \
  --test-mode \
  --output graph_test.svg \
  --ascii
```

## 5. Демонстрация работы (Этапы 4 и 5)

Для доказательства работоспособности программы в папке [`examples/`](examples/) сохранены результаты работы алгоритма для трех различных пакетов из тестового репозитория.

### 1. Порядок загрузки зависимостей (Этап 4)
В ходе работы была реализована топологическая сортировка для определения правильного порядка загрузки (сначала зависимости, затем сам пакет). 
*   Полный лог работы для пакета A: [`package_A.txt`](examples/package_A.txt)
*   Полный лог работы для пакета B: [`package_B.txt`](examples/package_B.txt)

**Пример вывода для пакета A (фрагмент):**
```text
--- Loading Order ---
D -> B -> C -> A
```
*(Как видно из вывода, пакет `A` загружается последним, так как он зависит от `B` и `C`, которые, в свою очередь, зависят от `D`)*.

### 2. Визуализация графа в D2 и SVG (Этап 5)
Программа генерирует исходный код на языке диаграмм D2 и сохраняет отрендеренные изображения в формате SVG. Вы можете открыть файлы ниже, чтобы увидеть графы:
*   Граф для пакета A: [`package_A.svg`](examples/package_A.svg)
*   Граф для пакета B: [`package_B.svg`](examples/package_B.svg)
*   Граф для пакета C: [`package_C.svg`](examples/package_C.svg)

**Пример вывода ASCII-дерева для пакета A:**
```text
--- ASCII Tree ---
|-- A
  |-- B
    |-- D
  |-- C
    |-- D
```

### Сравнение с выводом штатных инструментов
В рамках тестового режима я сравнивал граф с тем, что строит `dotnet list package --include-transitive`. Структура дерева совпадает. Отличия в реальном NuGet могут возникать из-за того, что официальный менеджер пакетов учитывает правила разрешения версий (Version Resolution) и целевые фреймворки (Target Frameworks), в то время как мой инструмент строит граф по прямым указаниям из `.nuspec` файла. Логика обхода графа в нашем инструменте полностью корректна.
